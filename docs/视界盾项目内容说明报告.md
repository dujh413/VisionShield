## 一、项目概述

视界盾主要解决学生在图书馆、自习室等公共空间使用电脑时，屏幕中的个人信息可能被旁人看到的问题。软件通过摄像头判断机主是否已确认、画面中是否出现其他人，同时自动获取桌面可见文字并判断敏感信息。在风险出现时提醒机主，遮蔽敏感文字及尚未完成分析的变化区域；环境恢复安全并持续稳定后，自动恢复正常显示。

项目按场景创新方向推进。软件是落地载体，场景需求、真实任务表现和用户体验是后续验证重点。首期建议聚焦“学生在公共学习空间查看、核对或填写个人材料”，使用虚构的联系方式、学号、账号等字段构建测试任务，再开展经同意的实际场景试用。

当前已提供统一入口、简约界面、后台托盘运行的Windows EXE便携预览版，完整解压即可使用。正式安装器、新电脑兼容及持续实人效果仍待完善。

## 二、用户操作与完整流程

### 2.1 首次使用

1. 配置本机开发环境和模型。
2. 双击仓库根目录的“启动视界盾.cmd”，打开主界面。
3. 暂停防护，在设置中选择“登记 / 更新机主”。
4. 本人确认登记画面后，点击“开始本人登记”。
5. 登记完成后启用防护，软件自动并行启动摄像头与文字识别。

登记采集12份符合条件的人脸特征，保存本地机主模板。已有模板在新登记完成前保留；日常使用自动读取模板，不需要每次低头、转头后重新登记。

### 2.2 日常运行

启动界面 → 启用防护 → 桌面采集与摄像头识别并行 → 文字识别与敏感规则判断 → 风险判断 → 提醒及区域遮蔽 → 风险稳定消失1秒后恢复。

软件主界面提供状态、启用/暂停、设置和后台运行入口。关闭主窗口后驻留系统托盘；退出软件时停止采集与推理并释放设备。默认打开界面不加载模型，启用后才加载，暂停后结束后端进程。

主显示器上的可见文字是当前主要保护范围。正常运行无需手动截图、框选或逐条确认敏感内容。

## 四、技术路线与实现方式

### 4.1 软件架构

软件采用轻量前端与独立后端进程。前端负责界面和托盘，后端服务负责采集、OCR、摄像头状态及保护调度。摄像头和OCR各自运行，保护控制不需要等待每次OCR推理完成。

| 模块 | 主要职责 |
|---|---|
| VisionShield.py、app_shell.py | 统一入口、界面、托盘、设置与后端生命周期 |
| guard_service.py | 后端服务启动、状态发送和停止清理 |
| camera_worker.py | 摄像头采集、人脸检测、机主验证与本人登记 |
| 视界盾开发中的身份模块 | 特征提取、模板比对、跟踪及风险状态基础 |
| screen_capture.py | 屏幕采集、显示器信息和画面更新 |
| ocr_worker.py | 后台OCR、增量处理及结果时间信息 |
| sensitive_rules.py | 文字规范化、敏感类别和邻近标签关联 |
| content_index.py | 按区域验证OCR结果，管理敏感框和待分析区域 |
| overlay_window.py | 桌面覆盖窗口与不透明模糊保护 |
| desktop_guard.py | 桌面识别、风险状态和遮蔽联动控制 |

前后端通过本机Qt通信与结构化状态消息协作。暂停和退出时结束摄像头、OCR与采集任务，释放图像和模型资源。

### 4.2 摄像头与机主识别

人脸检测使用YuNet，身份特征提取与模板比对使用SFace。摄像头图像进入检测与跟踪流程后，对满足质量条件的人脸进行特征匹配。

当前默认相似度阈值为0.45，需要连续5帧满足确认条件才确认机主。阈值和连续帧数是开发配置，后续需要通过多人的独立测试确定误确认与误拒绝情况。

机主未确认、检测到第二张脸、摄像头异常或状态过期时进入保护。机主重新出现后仍需确认环境安全；存在其他人时继续保护。

该模块目前判断的是“机主是否确认”和“是否多人”等风险信号。摄像头视场之外的人、画面中的人是否确实在看屏幕，以及距离与观看角度的精确判断，仍需要进一步研究与验证。

### 4.3 文字获取与敏感判断

当前软件主链路使用RapidOCR相关ONNX推理后端，在本机通过DirectML进行文字检测与识别，CPU作为可用后端之一。项目最初的PaddleOCR路线是开发起点，当前运行路径应以仓库实现和实际推理提供者为准。

采集图像只在内存中流转。OCR处理采用后台任务、最新帧调度、变化区域处理和稳定结果复用，避免不断积累等待处理的旧画面。

规则覆盖：

- 手机号与邮箱的格式匹配。
- 身份证号的格式、日期与校验码验证。
- 验证码、学号、账号、密码、地址和姓名等标签上下文。
- 标签与邻近值行的关联。
- 低OCR置信度文字的保守保护。

第一版主要按整条敏感文字行保护。地址多行关联和一般私人聊天仍需补充场景样本与语义模型，不能用规则命中结果代表所有隐私内容均被识别。

### 4.4 坐标有效性与保护调度

ContentIndex使用64像素网格比较画面变化。OCR返回后核对对应区域是否仍与当前画面一致，稳定区域保留有效结果，变化区域等待重新识别。

风险期间，旧敏感行发生变化时先保护整行；尚未分析的变化区域临时扩大遮蔽。初始化、结果失效或严重异常时可临时整屏保护。

这一机制可以减少旧坐标错位和推理等待期间的暴露，但屏幕采集和变化检测本身仍有延迟，需要实测“新内容出现到保护覆盖”的时间。

### 4.5 遮蔽与提醒

桌面保护由PySide6透明置顶窗口实现，普通区域透明，敏感区域绘制不透明的强像素化模糊图像。当前处理包含32像素级下采样、模糊插值和压暗；异常时使用不透明整屏保护。

遮罩需通过截图排除探针，避免OCR重复识别自身遮罩。控制逻辑还应兼顾坐标缩放、窗口移动、聊天滚动和通知弹出。

风险进入时通过托盘通知、提示音和界面状态提醒机主，通知冷却时间为10秒；遮蔽状态不受通知冷却影响。风险消失并稳定1秒后恢复，等待期间风险再次出现则取消恢复。

普通电脑屏幕显示的遮蔽效果对各观看方向相同。软件提供内容隐藏，不提供“机主可见、旁人因角度不同不可见”的硬件光学防窥效果。

## 五、已有测试与结果

以下汇总2026年10月3日的本机测试记录，本次报告整理没有重新运行设备测试。屏幕为2560×1600，OCR记录显示DirectML与CPU推理提供者；CPU/GPU具体型号尚未纳入完整测试登记，因此这些数字用于描述当前本机结果。

| 测试项目 | 已有结果 | 结果适用范围 |
|---|---|---|
| 屏幕采集 | 20秒观察184帧，约9.2帧/秒；帧龄中位数78ms，最大110ms | 帧龄不是完整防护响应时间 |
| 采集画面与遮罩排除 | 虚构色块/移动检查146次全部通过，遮罩采集排除通过 | 当前主显示器配置 |
| OCR小样本 | 4行虚构文字推理125—141ms，端到端157—188ms | 指定受控样本，非复杂整屏速度 |
| OCR缓存复用 | 一次稳定画面复用端到端约15ms | 没有重新推理，不能当成识别耗时 |
| OCR实际桌面 | 约137—138行文字，推理1484—1594ms，端到端1563—1656ms | 三次整屏记录，尚未普遍达到500ms |
| OCR冷启动 | 到就绪约3062ms | 独立OCR诊断，不等于整个软件全部就绪 |
| 实人身份测试 | 45.09秒、331帧，确认机主、失去确认后再次确认均出现 | 单人测试，未提供真实多人准确率 |
| 实人软件联动 | 服务运行、敏感文字发现、安全显示、风险模糊、恢复、提醒、停止检查均通过 | 风险来源为真实摄像头，未注入风险信号 |
| 模拟风险联动 | OCR定位、正常显示、风险模糊、恢复及资源停止检查通过 | 风险阶段由测试器注入，单独归类 |
| 代码测试 | 既有验收记录：桌面模块34项、机主状态7项通过 | 功能回归证据，不替代用户效果试验 |

早期10分钟诊断曾发现复杂桌面识别较慢、整屏变化使旧结果难以生效的问题，后续已经加入区域有效性核对。当前版本仍需重新开展较长时间的联合压力测试，才能确认修复后的稳定性。

前端此前实测空闲约69MB、暂停约70MB，仅说明轻量界面的占用。防护运行包含多个模型进程，完整系统CPU、GPU、内存与长时间增长情况仍需统一测量。

测试截图、桌面原文和人脸图像没有作为报告附件上传。报告只列必要的汇总指标，详细原始运行记录留在本机。

## 六、场景价值与当前不足

项目将环境感知与内容保护结合：机主独处且确认时正常显示，风险出现时优先保护敏感内容，减少反复手动隐藏窗口的操作。稳定结果复用和变化区域临时保护，使保护控制与较慢的文字推理解耦。

当前能够演示完整功能流程。要形成有说服力的场景创新成果，还需补齐以下证据：

| 当前不足 | 后续工作 | 应形成的证据 |
|---|---|---|
| 场景需求仍以项目设想为主 | 访谈和任务观察，明确高频信息与使用习惯 | 匿名需求记录、需求与功能对应表 |
| 复杂整屏识别慢 | UIA/Win32直读接入、OCR补充、区域调度和推理优化 | 各应用覆盖率、耗时分布及失败情况 |
| 风险判断相对粗 | 真人多人、不同位置、光照和动作测试 | 误拒绝、误确认、风险漏报及误报统计 |
| 敏感判断主要依赖规则 | 扩大虚构样本，评估语义分类和跨行关联 | 独立测试集、漏检与误遮数据 |
| 遮蔽实际效果尚待量化 | 不同距离、角度和字号下的字段辨认测试 | 旁观者辨认正确率与机主任务耗时 |
| 资源与稳定性证据不完整 | 联合长时间运行、暂停恢复和异常测试 | 全进程资源曲线、异常恢复和停机清理记录 |
| 新设备部署尚未验证 | 在功能稳定后打包并测试新机器 | 依赖清单、安装与启动记录、兼容范围 |

已有功能通过测试不等于已经证明校园应用效果。后续应设计对照：无保护、手动隐藏和视界盾自动保护，在同一类虚构材料任务中比较暴露情况、任务时间、打断次数及用户接受程度。

本报告不重新确认赛事年度规则或评分权重。正式提交前，应按实际参赛届次核对官方赛题、材料格式及评分要求。

## 七、下一阶段安排与分工

| 阶段 | A：摄像头与身份 | B：文字获取与集成 | C：规则与场景验证 | 阶段交付 |
|---|---|---|---|---|
| 第一阶段：稳定基线 | 真人多人、转头、低头及失联测试 | 联合长时间运行，登记完整硬件与资源 | 统一样本和故障用例 | 可复现基线、问题清单、验收表 |
| 第二阶段：降低延迟 | 稳定身份确认，减少状态抖动 | 接入UIA/Win32，OCR补充不可直读区域 | 检查坐标映射、漏检与误遮 | 各应用文字覆盖率及延迟报告 |
| 第三阶段：场景试验 | 配合真实位置风险测试 | 保障版本固定与记录方式一致 | 组织经同意的访谈和对照任务 | 需求证据、应用效果和失败分析 |
| 第四阶段：产品交付 | 完善登记和设备异常体验 | 单入口封装、安装与新机器验证 | 整理演示脚本、报告和操作说明 | Windows软件、演示视频与参赛材料 |

500ms应作为明确的优化目标：分别统计文字获取端到端延迟和风险信号到遮蔽的延迟，按应用、文字量和硬件记录中位数与P95。不能将500ms采集周期写成500ms识别速度，也不能将缓存复用速度写成新文字识别速度。目标是否达成应以独立测试结果为准。

## 八、数据管理与团队协作

正式仓库为公开的GitHub仓库VisionShield，完整功能位于main，本机源码入口为仓库根目录。访客仅可读取、fork和提交建议；受邀团队成员使用任务分支/PR，由所有者审查。main禁止强推和删除，所有者保留日常直推维护权限。

同步范围包括源码、依赖说明、项目文档和虚构测试样本。虚拟环境、模型缓存、机主模板、真实屏幕内容和运行日志留在各成员本机，不进入GitHub。

正常运行图像与识别文字在内存中处理，不建立持续累积的原文历史。用户设置、机主模板及必要的元数据/异常日志会持久保存到本机。应继续用长时间测试确认缓存有界及暂停清理效果，不能仅凭“内存处理”推断运行资源不会增长。

## 九、成果定位与交付清单

当前成果是一套已经打通摄像头识别、OCR、规则、提醒、模糊遮蔽和恢复流程的Windows开发版软件。接下来的重点是提升复杂画面文字获取速度，量化识别与保护效果，并用真实校园任务验证使用价值。

现阶段可供团队使用的内容包括：

1. 统一启动入口和后台托盘界面。
2. 本人登记与机主持久模板识别。
3. 桌面文字识别、敏感规则与区域有效性管理。
4. 风险提醒、区域模糊遮蔽、异常保护和延时恢复。
5. 已有功能测试、受控联动与单人实测结果。
6. 公开源码仓库、防护规则、协作约定、启动说明和内容说明报告。

进一步参赛材料应围绕需求依据、实际实现、验证数据和应用效果组织，所有功能与性能表述以固定版本的可复核结果为准。
