## 已采用的修改

前端启动后端时，在该进程的 `QProcessEnvironment` 中设置 `OPENBLAS_NUM_THREADS=1`。设置发生在后端导入 NumPy 之前，后续摄像头与 OCR 子进程继承这一环境；不修改系统环境变量或前端父进程的环境。

NumPy 在本机默认建立较多计算线程，导入后的私有内存约499.5MiB。相同环境下指定单线程后，OCR 进程在建立模型之前的私有内存从525.8MiB降到43.6MiB。短小的人脸特征矩阵没有必要为每个隔离进程建立这样的大线程池。OpenCV及ONNX Runtime各自的推理线程配置保持原有设置。

真实DirectML OCR对照使用三个虚构文字画面：500×300、1280×720及2560×1600，每个画面处理4次。模型、画面、固定形状预热和GPU适配器选择均相同：

| 指标 | 原环境 | 限制OpenBLAS线程 |
|---|---:|---:|
| 进程私有内存采样峰值 | 1997.8MiB | 1520.1MiB |
| 进程RSS采样峰值 | 581.0MiB | 576.0MiB |
| 文字、置信度、坐标结果 | 12份输出 | 与原环境12份全部一致 |
| 检测/识别实际providers | DirectML＋CPU | DirectML＋CPU |

私有内存峰值降低477.7MiB，约23.9%；RSS差别很小，不能将该结果写成物理驻留内存降低480MiB。每20ms采样，不能保证捕获所有瞬时峰值。这里只测一个OCR进程，未验证整套冻结软件的内存，更不能按进程数量简单推算全系统改善。

OCR推理耗时仍受画面大小和GPU负载影响；每种尺寸4次不足以证明性能百分比改善。该修复减少线程内存开销，不代表主界面闪烁或全部延迟已经消除。

另测关闭DirectML会话的CPU内存池，私有内存没有明显降低，因此未采用这一调整。未使用的文字方向分类器增加约3MiB初始化内存，与本轮主要问题不符，没有为此重写OCR预后处理。

## 人脸推理引擎实验

使用[OpenCV Zoo官方动态形状YuNet说明](https://github.com/opencv/opencv_zoo/tree/26cc381e4d2594bb9f47a26eb8fd96c94a13660d/models/face_detection_yunet)，在忽略目录中比较现有OpenCV推理与ONNX Runtime CPU推理。官方模型的Git LFS SHA256为 `ebafce4e3c118d6554634be5c27ab333b4c047a9a8c3faf1d7cf93101c22f0f0`，229,738字节；从固定提交下载并核验。两版模型的112个权重张量和106个计算节点逐一相同，仅输入高宽由固定值改为符号维度。模型目录的许可为MIT。

后处理参考[OpenCV 4.10.0 FaceDetectorYN实现](https://github.com/opencv/opencv/blob/4.10.0/modules/objdetect/src/face_detect.cpp)，保留BGR输入、32倍数补边、原有分数与NMS门限及五点顺序。没有读取机主模板或修改SFace。

三个公开人像合成画面、四种输入尺寸，共12组比较。每组5次推理，耗时汇总排除首轮。两种引擎的检测框、五点和分数最大数值差约0.000031；单次分区1280×864输入，OpenCV中位约75–77ms，ORT两线程约44ms，整帧960×540输入约31–32ms对18–19ms。

这个实验说明有进一步缩短分区扫描间隔的路径，但没有改变模型对严重模糊脸的识别能力。尚未接入正式摄像头链路，未修改生产模型或打包配置；不声称全屏幕/背景500ms覆盖或实人准确率已达标。后续需验证完整扫描调度、错误回退、机主特征兼容、CPU竞争及冻结包，再决定采用。

另以当前OpenCV检测器两线程运行11个公开合成场景、165帧，三个40像素低对比度且重模糊场景仍完全漏检，未采用增加OpenCV线程数的方案。上述公开样本都是离线算法实验，不代表人群统计或持续双人现场效果。
