# 人脸推理加速与扫描节拍验证

日期：2026-10-06。接续[后台计算线程与离线检测验证](后台计算线程与离线检测验证_20261006.md)，将同权重 YuNet 的 ONNX Runtime CPU 推理接入摄像头链路，并修正身后分区扫描的重复限频。本轮算法验证未打开摄像头、采集真实桌面或读取个人机主模板；实人双人测试按用户安排稍后进行。

## 本轮采用的修改

`视界盾开发/onnx_yunet.py` 提供与 OpenCV `FaceDetectorYN` 相同格式的检测框、五点和分数。会话使用 CPU provider、2 个算子内部线程、1 个算子间线程及顺序执行，关闭 CPU 内存池、内存模式和算子内部线程空转。关闭空转采用 ONNX Runtime 的 `session.intra_op.allow_spinning=0` 配置，目的是减少等待期间的 CPU 占用；本报告不据此推算全系统功耗或内存改善。[ONNX Runtime 线程配置说明](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)

输入保留 BGR 原始像素、右侧和底部补齐至 32 的倍数；解码保留三个 stride、`sqrt(cls*obj)` 分数、五点顺序、0.6 检测门限和 0.45 NMS 门限。NMS 使用与现有实现一致的整数框。SFace 模型、身份门限和机主模板没有修改。[OpenCV 4.10.0 解码实现](https://github.com/opencv/opencv/blob/4.10.0/modules/objdetect/src/face_detect.cpp)

摄像头循环已有约 100ms 的处理限频并消费最新画面，生产扫描器改为 `detail_interval=0`，避免再次用画面时间戳判断是否扫描。加速引擎启用时，弱焦点路径每帧轮转两个身后分区；原 OpenCV 回退路径仍轮转一个。强焦点路径原有的两分区调度、对比度辅助、弱检测确认、风险保持和身份检查继续生效。

加速模型或引擎初始化失败时，沿用原 OpenCV YuNet；运行中推理错误仍按摄像头异常处理并请求保护。没有通过降低检测门限、放宽身份条件或扩大用户指定遮蔽范围换取检测数量。

推理结果的全部输出均检查有限值，NaN/Inf不能被当作正常无脸。多个候选被NMS全部过滤时，返回与原检测器一致的 `None`，保留无脸结果契约。

## 最终源码的离线扫描节拍复测

测试机为 Windows 11，AMD Ryzen 7 7745HX（8 核 16 线程），Python 3.12.10、OpenCV 4.10.0、ONNX Runtime DirectML 1.24.4；本项人脸测试仅使用其 CPU provider，不调用 GPU。以两张公开肖像制作 1280×720 合成场景，覆盖空画面、单人、双人、20–80px 小脸、低对比度、模糊及人工遮挡等 11 个场景。样本数量不足以描述真实人群准确率。

以下直接调用最终源码 `FaceScanner.detect` 及正式适配器，包含有限值检查和NMS边界契约；通过构造参数比较三种调度，没有复制另一份检测实现。载入与结束时源码摘要一致。三种调度按场景交替测试，减少依次测试带来的负载漂移。先对 960×540、1280×864、640×640 几种几何输入预热；每个场景、每种调度运行 15 帧，其中前 3 帧为旁人出现前阶段、后 12 帧为检查阶段，共 495 帧。画面观察间隔至少 100ms；观察时间使用本机 `GetTickCount64`，分辨率约 15.625ms，推理耗时使用高精度 `QueryPerformanceCounter`。

以下耗时汇总每种调度的全部 165 帧，包含前置阶段，不包含模型加载。单帧耗时包含检测、焦点辅助及当帧轮转分区，未包含摄像头采集、机主特征匹配、跨进程传递、OCR、界面绘制或遮蔽完成时间。

| 调度方式 | 单帧中位耗时 | 单帧 P95 | 双人检查帧匹配 | 额外检测框 |
|---|---:|---:|---:|---:|
| 加速引擎，原调度 | 117.75ms | 144.39ms | 70/84 | 0 |
| 加速引擎，弱焦点双分区 | 140.37ms | 175.85ms | 70/84 | 0 |
| 加速引擎，弱焦点双分区且取消重复限频 | 140.32ms | 151.69ms | 70/84 | 0 |

三个方案都使用同一个加速引擎。该表衡量调度取舍，不能用第一行与第三行计算“换引擎加速百分比”。本次观察时间戳都达到100ms门限，三种方案各165帧均详细扫描，因此第二、三行工作量相同，耗时差异不能归因为取消限频减少计算。双分区增加当帧计算量，换取更密集的身后覆盖。70/84 是七个双人合成场景中后 12 帧的目标匹配计数，同一图片重复参与测试，不是 84 名人物或 84 段独立视频；零额外框也只适用于这些画面。

同一个身后分区的两次扫描完成时间仍可能相隔超过 500ms：

| 场景 | 原调度分区重访中位 | 双分区并取消重复限频 | 新调度分区重访 P95 |
|---|---:|---:|---:|
| 40px 清晰左侧小脸 | 578ms | 468ms | 469ms |
| 40px 低对比度、重模糊，分区交界处 | 578ms | 453ms | 453ms |
| 60px 低对比度、重模糊，右侧 | 578ms | 453ms | 469ms |

以上几类分区重访中位低于500ms，但单人230px场景的最终调度重访P95为530.65ms、最大547ms，仍不能保证每次低于500ms。分区重访间隔也不等于陌生人首次被确认或界面完成遮蔽的延迟。不能据单帧推理低于 200ms 宣称所有位置均在 500ms 内响应。

另用 18 个新画面时间戳复现重复门控：原 100ms 门控仅进行 11 次详细扫描；取消这一层门控后为 18 次。实际生产的摄像头循环限频仍存在，不会重复扫描同一个旧画面。

## 尚未解决的问题

40px、对比度 0.35、模糊参数 3、位于左侧的合成小脸，在三个方案中均为 0/12；交界处 40px 和右侧 60px 重模糊样本各为 11/12。更密集地扫描能够减少等待，无法使同权重模型识别此前完全漏检的严重模糊人脸。

本轮没有验证真实自动对焦、持续双人露脸、真实遮挡、旧机主模板匹配或摄像头与 OCR 并行时的竞争。外部 CPU 负载和热状态没有独立控制，短序列的中位与 P95 不能作为全部负载下的性能保证。主界面闪烁与用户指定范围的验证需依据相应软件联动测试，不能以本报告的离线检测结果代替。

后续实人测试应依次覆盖本人独处、旁人在身后左右持续露脸、稍远小脸、模糊或遮挡、旁人离开，并记录实际动作时间。需分别报告漏脸、机主确认、风险判断及恢复；检测不到人脸时继续保护的行为不能记作检测成功。预览仅在本人准备好后启动，画面不保存。

另在本机忽略目录研究SCRFD模型。2.5G、1280输入配合对比度增强的单一方案，在相同11类合成用例中匹配72/84个背景目标检查帧、没有额外框，40px左侧重模糊样本仍为0/12；重复静态帧不能当作独立视频或人群准确率。该方案尚未验证SFace身份匹配及产品联动。官方预训练权重仅限非商业研究，未加入正式源码或分发包；代码许可和权重许可分别适用。[固定版本的官方许可](https://github.com/deepinsight/insightface/blob/81929474ec02e54e3655f6841bced800009c592d/README.md#license)
