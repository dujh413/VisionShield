# 视界盾：实时文字获取与保护控制优化

## 1. 本轮落实的改动

最终目标仍是一个Windows软件。现在的脚本用于分阶段开发验收，最终由同一主程序管理摄像头、文字获取、敏感判定和遮罩。

| 路径 | 实现 | 目的 |
|---|---|---|
| 可直接读取的文字 | 标准Edit先读取可见行，其他支持控件使用UIA TextPattern | 避免文字先转成图片再识别 |
| 图片和自绘文字 | 本地PP-OCRv4 ONNX，DirectML GPU检测和识别 | 加速仍需要OCR的内容 |
| 推理输入 | 检测使用固定尺寸；识别按宽高比分组、固定4条批量和宽度；启动预热 | 减少新尺寸导致的首次推理开销 |
| 文字清晰度 | 检测缩放，识别从原始图像裁剪；坐标映射回原图 | 避免将低分辨率检测图直接用于文字识别 |
| 采集 | 独立线程每100ms尝试采集，队列只留最新帧 | 截图不阻塞界面和保护控制 |
| 控制 | Qt每20ms检查状态；OCR独立进程 | 风险信号不等待新OCR完成 |
| 重复内容 | 未变化复用，变化区增量识别；位置失效时保护未知区域 | 减少重复计算，避免错误复用旧坐标 |

检测最长边默认1536，固定检测尺寸512×384、1024×640、1536×960。识别宽度320、640、1280、2560预热；超过2560的长行仍可能触发新尺寸。OpenCV预处理使用单线程，减少与模型线程竞争。GPU通过DXGI适配器枚举选择本机独立显卡；界面就绪信息显示实际provider，缺少DirectML时使用CPU，速度需重新验收。

实现依据：[RapidOCR项目](https://github.com/RapidAI/RapidOCR)、[ONNX Runtime DirectML配置](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html)、[Microsoft可见文字范围](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-usingtextrangeobjects)。

## 2. 本机测试结果及范围

2026-10-02，Ryzen 7 7745HX、RTX 4070 Laptop，虚构文字样本，不保存桌面截图或文字原文。

| 测试 | 中位耗时 | 最大耗时 | 测量范围 |
|---|---:|---:|---|
| 标准Edit直读 | 2.2ms | 以自检输出为准 | 可见4行，预热后8次，仅读取 |
| 直读含通信和界面轮询 | 16ms | 31ms | 同一控件，不含之前等待采集；首次请求1219ms单独统计 |
| 普通字号整屏OCR | 340.4ms | 474.0ms | 2560×1600虚构图、暖机后5次，含增量模块处理，不含完整采集/通信/显示 |
| 普通字号变化区OCR | 388.9ms | 560.7ms | 同组样本，变化面积约5.5%，关键文字正确 |
| 小字整屏OCR | 263.6ms | 399.3ms | 12像素虚构字体，5次，预热宽度增加2560之前的结果 |
| 小字变化区OCR | 155.1ms | 450.8ms | 同组小字样本，变化面积约3.2%，关键文字正确 |
| 控制信号到测试遮罩绘制 | 9.3ms | 21.1ms | 虚构窗口、20次，本机UDP到Qt paintEvent，P95为20.9ms |

控制测试不包括摄像头识别、真实旁观者进入时刻和显示器扫描输出。上述OCR结果不是端到端响应，也不是整个软件的P95。样本数量少，负载和长行会造成波动；实测已出现超过500ms的峰值，不能据此保证所有场景均低于500ms。启动加载和预热只在启动状态处理，不伪装成运行过程耗时。

19项采集、规则、坐标更新与缓存测试通过。后台OCR虚构图像自检通过：4行、关键文字正确、3条敏感规则命中、未变化复用正确。遮罩采集排除探针本机通过，其他机器仍需启动验证。

## 3. 现在具体操作

关闭旧的OCR或混合预览进程，打开PowerShell：

```powershell
Set-Location -LiteralPath 'D:\ai比赛\VisionShield\视界盾桌面防护'
.\.venv\Scripts\python.exe hybrid_text_test.py --demo
```

等待初始化完成，把虚构文本编辑器和结果窗口并排放置。修改验证码、删除一行、滚动和移动窗口，观察左侧直读结果更新；右侧显示异步OCR补充。两个来源的时间不同，不直接合并坐标。关闭结果窗口应退出两个子进程和采集线程。

随后验收实际应用：

```powershell
.\.venv\Scripts\python.exe hybrid_text_test.py
```

将使用虚构内容的记事本、浏览器或聊天窗口置于前排。先观察来源：win32_edit或uia代表直读；OCR位于补充栏。应用没有公开完整可见文字时，仍需要OCR。当前混合预览只加速一个前排窗口，尚未把直读坐标接入桌面遮罩；desktop_guard.py已经使用异步采集和新OCR后端。

只看新OCR的框和敏感类别：

```powershell
.\.venv\Scripts\python.exe ocr_test.py --sensitive
```

迁移机器或更新依赖后，先安装 requirements-extra.txt，再从仓库根目录执行 Enable-GpuOcr.ps1。CPU 与 DirectML 发行包共享 onnxruntime 模块名，不能仅凭安装列表认定 GPU 已启用；脚本核对实际加载的运行时，并用虚构文本与 ORT profiling 验证检测和识别的 GPU 算子。封装前也应在实际构建环境运行该验证，固定验证后的运行时文件，保留模型和第三方许可。具体步骤见 docs/GPU_OCR启用与验证_20261005.md。

## 4. 实际场景验收标准

使用虚构手机号、验证码、邮箱和普通聊天，记录应用版本、字号、缩放、主题、读取来源、文字错误与坐标误差。检查小字号、深色主题、连续输入、通知、聊天滚动、窗口移动和GPU负载变化。测试覆盖到真实应用后，再统计至少100次事件的中位、P95、最大延迟与漏检率，不只看单次平均速度。

分别测量：

1. 内容发生变化到文字和敏感类别可用的端到端时间，包括采集等待。
2. 摄像头风险事件发出到遮罩绘制的控制时间。
3. 旁观者进入到遮罩实际显示的完整系统时间。

开发目标：支持应用的文字路径端到端P95小于500ms，保护控制收到有效风险事件后的绘制P95小于100ms。当前受控测试只证明部分环节具备这个速度，不是整机目标已全部完成。

风险存在且内容刚变化时，应先保护未完成分析的区域，再细化为敏感区域；此时不能等待OCR后才首次保护。桌面原型目前采用保守整屏临时保护。摄像头帧率、机主判断阈值和陌生人风险判定也决定完整系统速度，下一轮需要连同真实遮罩一起测量。

--det-long 2048用于小字漏检时对照精度与速度，默认界面仍为1536。控制自检显示虚构窗口，不采集真实文字。所有测试报告仅输出耗时、数量与通过状态；调试预览在内存显示当前文字，不新增历史截图或原文日志。
